    Lesson 9.4: std::expected, error codes, and choosing a strategy¶

    C++23 · about 12 minutes

    Why this matters¶

    std::optional tells you that something failed but not why. Exceptions tell you why, but they're invisible in function signatures and unavailable in some builds. std::expected<T, E> (C++23) is the middle path: a value or an error, explicit in the type, cheap, and works with -fno-exceptions. Let's see it — and then settle the big question: which tool when?

    std::expected¶

    std::expected<Header, ParseError> parse_header(std::span<const std::byte>);

auto h = parse_header(bytes);
if (!h) report(h.error());
else use(*h);

    Construct an error with return std::unexpected{ParseError::truncated};. Like optional, C++23 gives it and_then, transform, or_else and transform_error, so a pipeline of fallible steps reads top to bottom.

    std::error_code¶

    The older standard mechanism, used by <filesystem>, <system_error> and networking-style APIs. An error_code is an integer plus a category (generic, system, or your own), so codes from different subsystems don't collide. Many std functions have two overloads: one that throws std::system_error, one that takes std::error_code&.

    examples/week09/lesson04.cpp
    #include <cstdint>
#include <expected>
#include <filesystem>
#include <iostream>
#include <string>
#include <system_error>
#include <vector>

enum class ParseError { too_short, bad_magic, bad_channels };

std::string to_string(ParseError e) {
    switch (e) {
        case ParseError::too_short: return "too short";
        case ParseError::bad_magic: return "bad magic";
        case ParseError::bad_channels: return "bad channel count";
    }
    return "?";
}

struct Header { int channels; int rate; };

[[nodiscard]] std::expected<std::vector<std::uint8_t>, ParseError> check_size(std::vector<std::uint8_t> b) {
    if (b.size() < 6) return std::unexpected{ParseError::too_short};
    return b;
}
[[nodiscard]] std::expected<std::vector<std::uint8_t>, ParseError> check_magic(std::vector<std::uint8_t> b) {
    if (b[0] != 'S' || b[1] != 'N') return std::unexpected{ParseError::bad_magic};
    return b;
}
[[nodiscard]] std::expected<Header, ParseError> decode(const std::vector<std::uint8_t>& b) {
    if (b[2] == 0 || b[2] > 8) return std::unexpected{ParseError::bad_channels};
    return Header{b[2], (b[3] << 16) | (b[4] << 8) | b[5]};
}

void report(const std::vector<std::uint8_t>& bytes) {
    auto result = check_size(bytes).and_then(check_magic).and_then(decode)
                      .transform([](Header h) { return std::to_string(h.channels) + "ch @ " + std::to_string(h.rate) + " Hz"; })
                      .transform_error(to_string);
    std::cout << (result ? "ok: " + *result : "error: " + result.error()) << '\n';
}

int main() {
    report({'S', 'N', 2, 0x00, 0xBB, 0x80});
    report({'S', 'N', 2});
    report({'X', 'X', 2, 0, 0, 0});
    report({'S', 'N', 0, 0, 0, 0});

    std::error_code ec;
    auto size = std::filesystem::file_size("/definitely/not/here.wav", ec);   // non-throwing overload
    std::cout << "file_size failed? " << std::boolalpha << static_cast<bool>(ec)
              << " (no_such_file: " << (ec == std::errc::no_such_file_or_directory) << ")\n";
    (void)size;
    try {
        (void)std::filesystem::file_size("/definitely/not/here.wav");           // throwing overload
    } catch (const std::filesystem::filesystem_error& e) {
        std::cout << "filesystem_error code matches: " << (e.code() == std::errc::no_such_file_or_directory) << '\n';
    }
}

    Output:

    ok: 2ch @ 48000 Hz
error: too short
error: bad magic
error: bad channel count
file_size failed? true (no_such_file: true)
filesystem_error code matches: true

    The decision¶

    There's no single right answer, but here's a defensible default:

    Situation Use
    A bug (precondition violated, impossible state) assert / contract / terminate — don't "handle" bugs
    Rare failure, far from where it can be handled, exceptions enabled exception
    Failure is a normal, expected outcome, handled by the caller std::expected<T, E>
    "Not found" with no further information needed std::optional<T>
    Interop with OS / filesystem APIs std::error_code
    Constructors exceptions (or a factory returning expected)

    Mark result-returning functions [[nodiscard]] so ignoring an error is a warning. (std::expected itself is not marked nodiscard by every library, so put it on your functions.)

    Key takeaways¶

    Key takeaways

    • std::expected<T, E> makes failure explicit in the type and works without exceptions.
    • Chain fallible steps with and_then, map values with transform, map errors with transform_error.
    • std::error_code pairs a value with a category; many std APIs offer throwing and error_code& overloads.
    • Bugs → assert/terminate; expected outcomes → expected/optional; rare far-away failures → exceptions.

    Quiz¶

    Q1. How do you return an error from a function returning std::expected<int, std::string>?

    Show answer

    return std::unexpected{std::string{"message"}}; (or std::unexpected("message") where convertible).

    Q2. Why compare ec == std::errc::no_such_file_or_directory instead of ec.value() == 2?

    Show answer

    The comparison goes through error categories/conditions and is portable; raw values differ between platforms and categories.

    Q3. Should a violated precondition (a caller bug) be reported with std::expected?

    Show answer

    Usually no — bugs should be caught by assertions/contracts and fixed, not returned as recoverable errors.
