    Lesson 6.5: RTTI: typeid, dynamic_cast, and std::any¶

    C++20 · about 9 minutes

    Why this matters¶

    Sometimes you hold an Effect* and need to know: "is this actually a Reverb?" C++ can answer at run time with RTTI (run-time type information). It's useful, it's occasionally a design smell, and on embedded and some Android builds it's turned off entirely. Let's see the tools and their trade-offs.

    dynamic_cast¶

    dynamic_cast<Derived*>(base_ptr) returns a valid pointer if the object really is a Derived (or derived from it), and nullptr otherwise. With references, failure throws std::bad_cast. It only works on polymorphic types (at least one virtual function).

    typeid¶

    typeid(expr) returns a const std::type_info& describing the dynamic type for polymorphic glvalues. type_info::name() is implementation-defined (GCC/Clang return a mangled name like 6Reverb), so use it for debugging, not for logic. To use types as map keys, wrap them in std::type_index.

    std::any (C++17)¶

    std::any holds a value of any copyable type and remembers which one; std::any_cast<T> gets it back (throwing std::bad_any_cast on mismatch). It's handy for property bags and plugin metadata, but you lose compile-time type checking — prefer std::variant (Week 9) when the set of types is known.

    examples/week06/lesson05.cpp
    #include <any>
#include <iostream>
#include <map>
#include <memory>
#include <string>
#include <typeindex>
#include <typeinfo>
#include <vector>

struct Effect { virtual ~Effect() = default; };
struct Gain : Effect { float g = 1.0f; };
struct Reverb : Effect { float room = 0.5f; };

int main() {
    std::vector<std::unique_ptr<Effect>> fx;
    fx.push_back(std::make_unique<Gain>());
    fx.push_back(std::make_unique<Reverb>());

    std::map<std::type_index, std::string> names{{typeid(Gain), "Gain"}, {typeid(Reverb), "Reverb"}};
    for (const auto& e : fx) {
        const Effect& ref = *e;
        std::cout << "dynamic type: " << names[typeid(ref)];
        if (auto* r = dynamic_cast<Reverb*>(e.get())) std::cout << " (room=" << r->room << ')';
        std::cout << '\n';
    }

    try {
        Effect& first = *fx[0];
        auto& r = dynamic_cast<Reverb&>(first);   // it's a Gain: throws
        (void)r;
    } catch (const std::bad_cast&) {
        std::cout << "bad_cast: first effect is not a Reverb\n";
    }

    std::map<std::string, std::any> props{{"rate", 48000}, {"codec", std::string{"opus"}}, {"vbr", true}};
    std::cout << "rate=" << std::any_cast<int>(props["rate"])
              << " codec=" << std::any_cast<std::string>(props["codec"]) << '\n';
    try {
        std::cout << std::any_cast<double>(props["rate"]);
    } catch (const std::bad_any_cast&) {
        std::cout << "bad_any_cast: rate holds an int, not a double\n";
    }
}

    Output:

    dynamic type: Gain
dynamic type: Reverb (room=0.5)
bad_cast: first effect is not a Reverb
rate=48000 codec=opus
bad_any_cast: rate holds an int, not a double

    The design smell¶

    if (auto* r = dynamic_cast<Reverb*>(e)) r->set_room(0.8f);
else if (auto* g = dynamic_cast<Gain*>(e)) g->set_gain(2.0f);
// ... a growing chain of casts

    A chain of dynamic_casts usually means a virtual function is missing (e->apply_preset(p)), or that the set of types is closed and a std::variant + std::visit would be clearer and faster.

    No RTTI builds¶

    Many embedded and game builds compile with -fno-rtti (and the Android NDK historically defaulted to it; modern NDK CMake toolchains enable RTTI and exceptions by default). Without RTTI, dynamic_cast on polymorphic types and typeid don't compile, and std::any is unavailable with some libraries. Design libraries so the core doesn't require RTTI.

    Key takeaways¶

    Key takeaways

    • dynamic_cast checks the dynamic type: null pointer or std::bad_cast on failure.
    • typeid(...).name() is implementation-defined; use std::type_index as a map key.
    • std::any stores any copyable value with runtime type checks; prefer std::variant for closed sets.
    • Chains of dynamic_cast are a design smell; some builds disable RTTI entirely.

    Quiz¶

    Q1. What does dynamic_cast<D*>(p) return if *p isn't a D?

    Show answer

    nullptr. (The reference form throws std::bad_cast.)

    Q2. Why shouldn't program logic depend on typeid(x).name()?

    Show answer

    Its contents are implementation-defined (and often mangled); they differ between compilers.

    Q3. When is std::variant a better choice than std::any?

    Show answer

    When the set of possible types is known at compile time: variant is type-checked, needs no heap allocation, and supports exhaustive std::visit.
